# Colossus UI

This Storybook documents the `web/` frontend: the shared design system, the feature components and the architecture rules that keep them apart. Every story renders from fixtures and needs no running backend.

## Adding a story

**Where the file goes.** Put `Name.stories.tsx` in the same folder as the component. A component that is internal to a feature (for example `ColorEncodingEditor`, which the feature `index.ts` does not export) can only be reached from inside its feature, so colocation is what lets it be documented.

Stories that belong to no single component live under `.storybook/`: `docs/` for MDX pages and `foundations/` for the token pages. `architecture.test.ts` scans `.storybook` as well, and treats it as outside every feature, so code there may import a feature only through its `index.ts`.

Stories never reach the product build or the unit tests:

- `tsconfig.app.json` excludes `*.stories.ts(x)`; `tsconfig.storybook.json` type-checks them together with `.storybook`.
- The `unit` project only matches `*.test.ts`.
- Nothing imported from `src/app/main.tsx` imports a story.

**Title.** `Components/<File>`, `Maps/<Component>`, `Sources/<Component>` or `Map Viewer/<Component>`. The order in the sidebar is set by `storySort` in `.storybook/preview.tsx`.

**Documentation.** Put explanations in `parameters.docs.description.component` (the component) and `parameters.docs.description.story` (one story), or in MDX. Describe props with `argTypes[...].description`. Product components carry no documentation comments for Storybook.

**Mock data.** Fixtures live in `.storybook/fixtures/` and are typed with `@/types/*`, so a change to an API type breaks them at compile time. Optional fields are omitted rather than set to `null`, as the API does. Builders such as `managedMap(overrides)` and `bakeRun(id, overrides)` create variations. Stories import them by relative path.

**Providers.** `.storybook/support/withAppProviders.tsx` is a global decorator that wraps every story in a fresh `QueryClient` (queries do not retry) and a `MemoryRouter`. Components that use TanStack Query hooks or router links need nothing else.

**Network.** Components that fetch data run their real hooks and `api/` functions. Replace `fetch` for the duration of a story with `mockApi` from `.storybook/support/mockApi.ts`:

```ts
beforeEach: () => mockApi([
  { method: 'GET', path: '/maps/map-1/runs', reply: () => ({ body: { runs: [] } }) },
]),
```

Paths are relative to `API_BASE`. A request with no matching route gets a 404 response. `mockApi` returns a function that restores `fetch`, which Storybook calls after the story. `neverResolves` keeps a request pending, to show a loading state.

**The test gate.** Every story is a test. It must render without errors and, if it has a `play` function, finish it. After that, the accessibility check runs with `a11y.test: 'error'`, in both themes. Fix the component or the story instead of excluding a rule.

**Stylesheets.** `.storybook/preview.tsx` loads the design tokens and primitives, `src/app/managementStyles.scss` (the management stylesheets, shared with `src/app/main.tsx`), the sources and viewer stylesheets and `.storybook/workbench.scss` (story-only layout helpers).
